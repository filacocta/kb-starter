Getting Started - Workflow View

The Knowledge Base, end to end

A personal, LLM-agnostic research vault: you capture sources once, an agent ingests them into structured source notes, then synthesises them into a browsable wiki. Everything is plain Markdown in an Obsidian vault — the agents and scripts are just disciplined hands on top of it.

This page explains the big picture: how knowledge flows in, the nine skills that move it, the scripts underneath, and the rules that keep it trustworthy. Toggle the tab above to compare with the system-oriented write-up.

1 · The mental model

Capture-once, synthesise-later

The cost of losing a good source is high; the cost of an unprocessed link is low. So the front door is friction-free — drop a URL anywhere — and the heavy thinking (reading, connecting, writing) happens later, in batches, by an agent.

Sources → Wiki

Raw material lands as source notes (one per URL/PDF). Once a topic has enough of them, synthesis distills recurring concepts and entities into wiki-style articles that link back to their sources. You read the wiki; the sources are the evidence.

Authorship guard (non-negotiable): agents only ever touch files inside knowledgebase/ that carry author: kb-bot frontmatter. Nothing else is created or modified. This is what makes the vault safe to let an agent loose in.

3 · The nine skills

Skills are invoked as slash commands (e.g. /kb-ingest <url>). Agent-specific config sets KB_ROOT and VAULT_NAME; the durable contract is the KB's _schema.md, _rules.md, and shared _tools/.

4 · The scripts underneath (_tools/)

Skills don't reinvent fetching/parsing in prose — they call real, tested scripts. The important ones:

  • kb-prep-item.py — one-call pre-fetch prep: dedup check, mirror rewrite, media discovery.
  • kb-tweet-fetch.py — full tweet text + quote + thread + X-Articles (via fxtwitter).
  • kb-video-analyze.py — transcript + slide-OCR + figure vision for video sources.
  • kb-media-capture.py / kb-headless-capture.py — figure/image capture (incl. headless Chromium).
  • kb-checkoff.py — mark a reading-list item in place (the "mark" verb; shared write path).
  • kb-promote.py — move a queue line between ladder sections, e.g. Pending→Approved→Auto-approved (the "move" verb).
  • kb-capture-url.py — add a new URL to a topic's ## Pending or the global inbox (the "add" verb).
  • kb-seen.py — dedup against already-ingested URLs.
  • kb-lint.py — the lint engine behind /kb-lint.
  • kb-derive-dive-queue.py — regenerate the research dive queue.
  • kb-obsidian-cli.py — emit obsidian:// citation links.

6 · Schema & the rules that keep it honest

Note types

sourceconcept / entitysynthesismetaproject

Every note carries frontmatter: author: kb-bot, type, topic, title, status, tags, related, and (for sources) origin/mirror/ingest_status.

Load-bearing rules

  • Authorship guard — only operate on author: kb-bot files; never write outside knowledgebase/.
  • Rule 18 — never blind-ingest an error / rate-limit response; mark for retry instead.
  • Rule 29 — capture only contextually-relevant media; keep media links intact.
  • Rule 30 — transport rewrites (e.g. x.com → fxtwitter) record canonical as origin, mirror as mirror.
  • Gated-source ladder — on 403/429/JS-shell, try an un-gated API/docs host, then a headed browser, before giving up.

7 · Where this dashboard fits

The KB Workflow Dashboard (this app) is a read-only window onto the live vault: it shows the active checkpoint, the global URL inbox, per-topic reading-list queue counts, the dive queue, kb-feed state, and recent _log.md entries — so you can see what's waiting without opening Obsidian. Future write actions should go through named shared-tool commands, confirmations, and logs; the browser should not edit Markdown directly.

8 · Source clusters can become skills, but only after synthesis

A book, article, or Gist does not automatically become a skill. Keep long-form raw files in a cataloged custody path outside topic folders, then ingest only the sections that matter to each topic. First synthesize the repeatable procedures, critique lenses, decision rules, examples, and failure modes. Existing skill artifacts should be reviewed in scratch: keep the original checkout intact, normalize package layout, validate the skill shape, and compare it against the KB synthesis. Promote to a skill only when the material improves a task an agent can actually perform, and test the package before installing it. If a skill references support files such as references/tufte-principles.md, the installed package must preserve that layout.
