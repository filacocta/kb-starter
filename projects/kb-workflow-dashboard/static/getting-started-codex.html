Knowledge Base Workflow Dashboard

Getting started with the KB

This vault is a personal, Obsidian-readable knowledge base built on sbuffkin/kb-starter conventions. It is LLM-agnostic: plain Markdown, YAML frontmatter, wikilinks, shared rules, and helper scripts form the contract any agent can follow.

capture once synthesise later source notes -> wiki summary-first navigation
Runtime config agent KB config KB_ROOT: /path/to/vault/knowledgebase VAULT_NAME: <vault name> Agent workflows read this at startup.

Big Picture

Use the KB as a research pipeline, not a dumping ground.

Sources Are Raw Evidence

URLs, PDFs, transcripts, tweet mirrors, and media records become immutable type: source notes under a topic's sources/ folder.

Wiki Notes Are the Product

Concept, entity, and synthesis notes turn accumulated sources into browsable prose. Stubs are allowed after one source; fuller articles start when two or more sources support a topic.

Agents Read Small First

The navigation path is _index.md, then relevant _summary.md files, then individual notes only as needed. This keeps context windows focused.

End-to-End Workflow

Capture candidates, ingest evidence, synthesise the wiki, maintain structure, then query and loop project knowledge back in.

1. Capture

Telegram bot sends links through the kb-feed pipeline into per-topic reading-list.md queues.

Queue source candidates
2. Ingest

/kb-ingest handles one source interactively. /kb-queue batches approved items. /kb-auto processes ## Auto-approved unattended.

Write source notes
3. Synthesise

/kb-synthesise turns source folders into concept, entity, and synthesis notes with citations and backlinks.

Build the wiki
4. Maintain

/kb-lint checks broken wikilinks, orphan pages, incomplete frontmatter, contradictions, stale sources, and media integrity.

Find structural problems
5. Query

/kb-ask answers questions, browses topics, and surfaces research queues using summary-first navigation.

Use the knowledge
6. Project Loop

/kb-scan starts sessions, /kb-wrap records stopping points, and /kb-project-init creates new project entries.

Keep work state durable
Project rhythm: start with /kb-scan to recover prior decisions and open questions, use /kb-project-init when a substantive project has no KB entry, and end with /kb-wrap so decisions, status, and follow-ups are not trapped in chat.

KB Skills And Meta-Skills

These slash-style skills are agent workflows, but their behavior is defined against the shared KB schema, rules, and tools.

/kb-ask

Scoped KB session

Query, browse, or discuss KB content using schema, rules, index, summaries, and Obsidian citations.

Use when: you want an answer from the KB, topic browsing, or a research queue view.

/kb-auto

Headless autonomous ingestion

Processes URL-first items under topic ## Auto-approved sections one at a time, deduping before fetch and checkpointing aggressively.

Use when: a cron or overnight unattended run should ingest pre-approved sources.

/kb-ingest

Single-source research session

Fetches one URL or PDF, discusses it, surfaces connections, identifies concepts, and writes only when ready to commit.

Use when: you want to actively explore one source instead of silently batch-processing it.

/kb-lint

Health check

Audits a topic or all topics for broken links, orphan pages, missing stubs, frontmatter gaps, contradictions, stale sources, and media integrity.

Use when: synthesis is done or a topic feels structurally messy.

/kb-project-init

New project entry

Reads project source material and creates projects/<slug>/_summary.md from the standard project template.

Use when: starting substantial work on a project with no KB entry yet.

/kb-queue

Batch reading-list processing

Reads queued URLs or PDFs, presents an approval checklist, then ingests approved items with checkpoint and resume support.

Use when: you want to work through a topic backlog or process multiple sources.

/kb-scan

Light orientation scan

Reads the index and relevant project/topic summaries, then surfaces directly applicable decisions, constraints, and open questions.

Use when: starting a work session on a named topic or project.

/kb-synthesise

Source notes to wiki

Builds a concept/entity inventory, applies page thresholds, proposes a plan, then writes wiki notes and updates summaries.

Use when: raw sources have accumulated after ingestion or queue work.

/kb-wrap

Session closeout

Updates project summaries, captures new topic knowledge, records decisions and open questions, and appends to the KB log.

Use when: a feature, investigation, or project session reaches a natural stopping point.

$book-to-skill

Source cluster to skill

Evaluates books, long-form PDFs, article clusters, and external skill artifacts before any candidate skill is created or installed.

Use when: source synthesis may justify a reusable agent procedure, critique checklist, or eval fixture.

Shared Helper Scripts

These scripts are real scaffolding under knowledgebase/_tools/; skills call them instead of hand-editing queues or reimplementing transport logic.

  • kb-prep-item.py - read-only pre-fetch prep: dedup, mirror rewrite, and optional media discovery.
  • kb-checkoff.py - race-safe queue mutation under .kb-write.lock; updates allowed checkbox states and refreshes _dive-queue.md.
  • kb-seen.py - canonical URL dedup from successful source-note origin: and mirror: frontmatter; failed ingests stay retryable.
  • kb-derive-dive-queue.py - derives the read-only root research dashboard from topic ## Auto-approved queues and research-ideas.md.
  • kb-lint.py - structural lint engine for frontmatter, links, reading-list shape, topic files, and media checks.
  • kb-media-capture.py - discovers and captures source media with provenance, hashing, license posture, and chrome filtering.
  • kb-headless-capture.py - Playwright fallback for JS-rendered images and element screenshots when static scraping misses content.
  • kb-tweet-fetch.py - fetches structured tweet or thread data through fxtwitter with retry/backoff behavior.
  • kb-video-analyze.py - creates structured video ingestion artifacts using metadata, transcripts, keyframes, OCR, and optional summaries.
  • kb-obsidian-cli.py - optional read-only bridge to the Obsidian CLI for diagnostics and searches when the desktop app is available.

KB Layout

The live index lists topics, projects, note counts, source counts, and the latest ingestion date. Starter installs begin with a small scaffold and grow from there.

knowledgebase/ _index.md _log.md _schema.md _rules.md _checkpoint.md _dive-queue.md # generated/read-only _templates/ _media/ images/ videos/ audio/ topics/ <topic>/ _summary.md reading-list.md sources/ notes/ concepts/ entities/ media/ syntheses/ projects/ <slug>/ _summary.md _todos.md notes/

Root Navigation

_index.md is the top-level map. Agents read it first, then topic or project summaries. _log.md records operations. _checkpoint.md makes long operations resumable. _schema.md and _rules.md define the cross-agent contract.


Topic Shape

Each topic keeps raw source notes in sources/, wiki output in notes/, queued URLs in reading-list.md, and a compressed orientation file in _summary.md.


Project Shape

Projects live under projects/<slug>/. The summary captures LLM orientation and project direction, while _todos.md tracks project work.

Schema Essentials and Rules

The rules are designed so multiple agents and scripts can work safely in the same vault.

Rule 1: Authorship Guard

Never create or modify anything outside knowledgebase/. Existing files must have author: kb-bot frontmatter before an agent writes them. When in doubt, do not write.

Rule 18: Failed Fetches

Do not blind-ingest errors, blank pages, wrong redirects, rate limits, or blocked responses. Log failures in source context and reading lists; use ingest_status: failed for retryable failed source records.

Rule 29: Media

Media discovered during ingestion is provenance. Source-note media: blocks are frozen at initial write; later OCR, transcripts, and analysis belong in separate type: media-description notes.

Rule 30: Mirrors

Some hosts are rewritten at fetch time. For example, x.com and twitter.com use fxtwitter-style mirrors. Keep the canonical URL in origin: and the actual transport URL in mirror:.

Note Types

Core types include source, concept, entity, synthesis, meta, and project-oriented files such as summary, todos, and project notes. Concept and entity notes are the browsable wiki layer; synthesis notes are cross-cutting analyses.

Dashboard Operations

The dashboard is an attention console first. Live writes should arrive through explicit shared-tool actions, not browser-side Markdown editing.

Starter vs live app

The starter repo ships the sanitized app scaffold. A local live copy can sit beside the vault and point at the real KB root. Shared code should stay mirrored.

Safe action path

First interactive buttons should call allowlisted tools such as lint, dive-queue regeneration, and locked checkoff commands with confirmation and logs.

Skill handoffs

Agent/skill execution should start as copyable handoff prompts. CLI launches need visible prompts, checkpoints, transcripts, cancel behavior, and post-run lint.

Artifact review

Cloneable Gists/repos should be checked in scratch, normalized, validated, and compared against KB synthesis before any install or starter inclusion.
